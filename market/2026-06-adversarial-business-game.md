# Adversarial Business Game: How We Make It Fail Convincingly

Date: 2026-06-16.
Purpose: identify the version of the strategy that looks smart, sounds convincing, and still leads to wrong work, bad positioning, or no repeat orders.

## Setup

Game rule: imagine we are trying to fail, but not obviously. We need a result that looks analytical, has tables and confident language, yet sends Vlad and Nastya into the wrong actions.

This is not final rewrite. This is the opponent's approval brief before improvements.

## Failure Mode 1: Beautiful Generic Kworks

What failure looks like:

1. We publish polished cards about "help with tasks", "texts", "AI", "Excel", "student work".
2. The copy is clean, but a buyer cannot instantly understand why choose us.
3. We blend into hundreds of sellers.

Why it is convincingly wrong:

1. It feels broad and flexible.
2. It creates an illusion that more services means more chances.
3. It uses all skills but does not create a sharp entry point.

Countermove:

1. Nastya starts with OSV/1C/acts and documents.
2. Vlad starts with ТЗ/Gantt/Codex and B2B/AI workflow.
3. Student/content/routine work stays secondary.

## Failure Mode 2: Mixed Identity

What failure looks like:

1. Nastya's account sells React, AI agents, webhooks and hard automation.
2. Vlad's account answers accounting/legal tasks without the right face.
3. The client feels something is off.

Why it is convincingly wrong:

1. Internally both can use each other's help.
2. The team really has combined skills.
3. But Kwork buyers judge the profile, not internal workflow.

Countermove:

1. Public responsibility stays clear.
2. Internal help is invisible operationally, not part of the promise.
3. The account split file remains the routing law.

## Failure Mode 3: Historical Data Pretends To Be Fresh

What failure looks like:

1. We use the 2026-05-27 local Kwork scrape as if it is current on 2026-06-16.
2. We rank competitors by stale counts.
3. We build copy and pricing around outdated visible prices.

Why it is convincingly wrong:

1. The dataset is large.
2. The patterns are probably still useful.
3. The numbers look precise.

Countermove:

1. Label it as historical category shape.
2. Run a fresh manual/current competitor pass before final pricing.
3. Keep exact current claims out of public copy.

## Failure Mode 4: Gross Economics Masquerades As Net Profit

What failure looks like:

1. We call 1500-2300 RUB/hour "effective" but ignore commission, payment costs, tax, revisions and chat time.
2. We accept small tasks that look profitable in a table.
3. First orders eat hours and kill momentum.

Why it is convincingly wrong:

1. The math is present.
2. The rates are plausible.
3. But the formula is missing real leakage.

Countermove:

1. Recalculate net rate after commission/tax path.
2. Add communication and revision multiplier.
3. Set a floor: no manual task below the approved net hourly rate unless it buys proof.

## Failure Mode 5: Legal Strength Turns Into Legal Overclaim

What failure looks like:

1. We sell "арбитраж", "УФАС", "договоры" as if we guarantee a legal result.
2. A client reads it as lawyer-style representation.
3. Scope and liability expand beyond the real offer.

Why it is convincingly wrong:

1. The words match real client demand.
2. There are actual skills in documents and protocols.
3. But the boundary is professional risk.

Countermove:

1. Sell document order, chronology, risk table, protocol, claim logic and questions.
2. Never sell court outcome.
3. Add boundary phrases into every relevant card and response.

## Failure Mode 6: We Chase Exchange Noise Instead Of Fit

What failure looks like:

1. We respond to everything from 1000 to 7000 RUB.
2. We win a few random jobs.
3. Profile gets filled with low-margin unrelated history.

Why it is convincingly wrong:

1. First money feels like validation.
2. Kwork rewards activity.
3. But random orders train the account in the wrong direction.

Countermove:

1. Daily hunt uses a decision filter.
2. Each response must map to a target Kwork direction.
3. Orders outside target can be taken only if they produce reusable proof.

## Failure Mode 7: Portfolio Is Promised But Not Built

What failure looks like:

1. Strategy says "proof matters".
2. Cards say we can do OSV, contracts, Codex workflows, КП.
3. Buyer sees no anonymized examples.

Why it is convincingly wrong:

1. Internally we know the skills are real.
2. The repo has lots of evidence.
3. Public buyer does not see the repo context.

Countermove:

1. Build 6 small proof artifacts before aggressive publication.
2. Each proof artifact must be privacy-safe.
3. Link or screenshot them in Kwork portfolio where allowed.

## Failure Mode 8: The Copy Is Too Clever

What failure looks like:

1. We overuse "Шеймо-стиль", irony, inside references and dense explanations.
2. The copy sounds alive, but the client has to decode it.
3. Buyer picks a simpler seller.

Why it is convincingly wrong:

1. The style feels ours.
2. It avoids boring HR language.
3. But Kwork is not a long-form essay.

Countermove:

1. First screen: what I do, what I need, what you get.
2. Derzost is allowed only where it sharpens trust.
3. No long metaphors in service cards.

## Failure Mode 9: Too Many Cards Too Early

What failure looks like:

1. We publish 10-12 Kworks at once.
2. None gets enough attention, examples or testing.
3. We cannot understand what works.

Why it is convincingly wrong:

1. More cards feels like more market coverage.
2. We already have drafts.
3. But no feedback loop forms.

Countermove:

1. Publish 4-5 first.
2. Send targeted responses for 7 days.
3. Kill, rewrite or expand only from response data.

## Failure Mode 10: We Let The Strategy Become The Work

What failure looks like:

1. More matrices, more prompts, more analysis.
2. No live offers sent.
3. No portfolio artifacts produced.

Why it is convincingly wrong:

1. The analysis keeps improving.
2. It feels responsible.
3. But Kwork needs visible movement.

Countermove:

1. Strategy changes must produce one of four outputs: card, response, proof artifact, tracker row.
2. Any new analysis has a 24-hour action attached.
3. The first week target stays 50 targeted responses and 4 proof artifacts.

## Improvement Tracks For Operator Approval

Approve one or several:

1. `A1 Fresh market pass`
   - Refresh current Kwork competitors and active orders.
   - Output: updated ledgers and exact current warnings.

2. `A2 Net economics`
   - Verify commission/tax path and recalculate hourly rates.
   - Output: net-rate table and minimum price rules.

3. `A3 Copy-paste cards`
   - Rewrite top 5 Kwork cards fully: title, category, description, packages, options, client requirements, tags, FAQ.
   - Output: one human-ready file.

4. `A4 Response operating system`
   - Build daily order-hunt tracker and response templates per direction.
   - Output: CSV or Google-Sheets-ready table.

5. `A5 Proof pack`
   - Create anonymized samples: OSV, contract/protocol, ТЗ/Gantt, B2B КП, Codex workflow, Excel/CRM table.
   - Output: portfolio-ready proof list and files.

6. `A6 Claude/Codex reconciliation`
   - Compare Claude raw files against Codex output and create one canon.
   - Output: conflict table and final merge recommendations.

7. `A7 Covers and visual proof`
   - Produce 660x440 Kwork covers for approved first cards.
   - Output: image assets with no tiny unreadable text.

8. `A8 7-day experiment`
   - Start from actual daily responses and record results.
   - Output: real conversion data instead of only strategy.

## What Can Be Deduced Further

1. Demand velocity, not just demand presence.
   - Need repeated scans or logged response counts over several days.

2. Competition per request.
   - Use visible offers count on each order where available.

3. Real delivery friction.
   - Add chat, revisions, file cleanup and client delay to each direction.

4. Account reputation risk.
   - Decide which first orders build the right public history.

5. Proof leverage.
   - Some jobs are worth taking cheaply only if they generate a public proof artifact.

6. Cross-sell map.
   - OSV task can lead to Excel automation, contract review, monthly support.
   - ТЗ task can lead to Codex workflow, B2B КП, prototype.

7. Kill criteria.
   - A Kwork with no messages after defined exposure and responses should be rewritten or buried.
